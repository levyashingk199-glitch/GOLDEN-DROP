# 📋 Правила работы агентов

## ⚠️ ОБЯЗАТЕЛЬНО К ПРОЧТЕНИЮ ПЕРЕД НАЧАЛОМ РАБОТЫ

Каждый агент **ОБЯЗАН** прочитать этот файл и файлы `task.md`, `done.md` перед тем как писать хоть одну строку кода. Нарушение этих правил ведёт к конфликтам, потере прогресса и дублированию работы.

---

## 1. Система отслеживания прогресса

### 1.1 Три файла — источник истины

| Файл | Назначение | Кто обновляет |
|---|---|---|
| `docs/task.md` | **Текущие задачи** — что сейчас в работе и что ещё не начато | Агент, берущий или завершающий задачу |
| `docs/done.md` | **Завершённые задачи** — лог выполненного с деталями | Агент, завершивший задачу |
| `docs/rules.md` | **Правила** — этот файл, не менять без согласования | Только координатор |

### 1.2 Жизненный цикл задачи

```
📋 BACKLOG (task.md)  →  🔨 IN PROGRESS (task.md)  →  ✅ DONE (done.md)
     ↑                        ↑                           ↑
  Не начата              Агент работает             Перенесена из task.md
  Никто не взял          Указан исполнитель         Записаны детали
```

### 1.3 Правила работы с task.md

**Перед началом работы:**
1. Прочитай `task.md` ЦЕЛИКОМ
2. Найди задачу со статусом `📋 BACKLOG`
3. Убедись, что все её зависимости (`depends_on`) имеют статус `✅`
4. Измени статус задачи на `🔨 IN PROGRESS`
5. Запиши своё имя/ID в поле `assignee`
6. Запиши текущую дату/время в поле `started_at`
7. Только после этого начинай писать код

**Во время работы:**
- Обновляй поле `progress` в task.md каждый раз, когда завершаешь значимый подэтап
- Если задача блокируется — измени статус на `🚫 BLOCKED` и укажи причину

**После завершения:**
1. Измени статус на `✅ DONE` в task.md
2. Перенеси запись в `done.md` с полной информацией:
   - Какие файлы созданы/изменены
   - Какие компоненты реализованы
   - Что тестировалось
   - Известные ограничения
3. Удали задачу из task.md (оставив только в done.md)

### 1.4 Формат задачи в task.md

```markdown
### TASK-{номер}: {Название}
- **Статус:** 📋 BACKLOG | 🔨 IN PROGRESS | 🚫 BLOCKED | ✅ DONE
- **Фаза:** {1-7}
- **Приоритет:** 🔴 HIGH | 🟡 MEDIUM | 🟢 LOW
- **Зависимости:** TASK-{X}, TASK-{Y} или "нет"
- **Исполнитель:** {имя агента} или "не назначен"
- **Начато:** {дата-время} или "-"
- **Прогресс:**
  - [ ] Подзадача 1
  - [ ] Подзадача 2
  - [ ] Подзадача 3
- **Заметки:** {любая полезная информация}
```

### 1.5 Формат записи в done.md

```markdown
### ✅ TASK-{номер}: {Название}
- **Фаза:** {N}
- **Исполнитель:** {имя}
- **Период:** {начало} → {конец}
- **Созданные файлы:**
  - `src/components/case/CaseCard.jsx` — карточка кейса
  - `src/hooks/useCaseOpen.js` — хук открытия кейса
- **Изменённые файлы:**
  - `src/Router.jsx` — добавлен маршрут /cases/:id
- **Установленные пакеты:** framer-motion, canvas-confetti
- **Что сделано:** краткое описание
- **Известные проблемы:** (если есть)
```

## 2. Правила работы с кодом

### 2.1 Перед написанием кода

1. **Прочитай документацию фазы** — соответствующий `phase-{N}-*.md` файл
2. **Прочитай `architecture.md`** — конвенции именования, структура, паттерны
3. **Прочитай `data-models.md`** — модели данных, форматы API
4. **Проверь существующий код** — не дублируй то, что уже написано
5. **Проверь task.md** — не бери задачу, которая уже в работе

### 2.2 Во время написания кода

| Правило | Описание |
|---|---|
| **Один файл = один компонент** | Не складывай несколько компонентов в один файл |
| **Именование** | PascalCase для компонентов, camelCase для хуков/утилит (см. architecture.md) |
| **Импорты** | Группируй: react → библиотеки → компоненты → утилиты |
| **Стилизация** | Только TailwindCSS + DaisyUI, никакого inline CSS и CSS-модулей |
| **Состояние** | Zustand для глобального, useState для локального, React Query для серверного |
| **API вызовы** | Только через модули в `src/api/`, никогда напрямую из компонентов |
| **Типы данных** | Следуй моделям из `data-models.md` |
| **Редкости** | Используй константы из `src/utils/rarities.js`, не хардкодь цвета |

### 2.3 Запрещено

- ❌ Менять конфигурационные файлы (`vite.config.js`, `tailwind.config.js`) без явной необходимости
- ❌ Устанавливать пакеты, не указанные в плане, без обоснования в task.md
- ❌ Удалять или переименовывать существующие файлы без записи в task.md
- ❌ Менять API-контракты (форматы запросов/ответов) из `data-models.md` без обновления документации
- ❌ Писать TypeScript (проект на JSX)
- ❌ Использовать CSS-in-JS библиотеки (styled-components и т.д.)
- ❌ Создавать файлы вне структуры, описанной в `plan.md`

## 3. Правила работы с документацией

### 3.1 Документация — это контракт

Файлы в `docs/` — это **контракт между агентами**. Каждый агент обязан:

1. **Читать** документацию перед работой
2. **Следовать** описанным в ней решениям
3. **Обновлять** её при отклонениях от плана

### 3.2 Когда нужно обновить документацию

| Ситуация | Что обновить |
|---|---|
| Добавил новый пакет | `plan.md` → таблица зависимостей |
| Создал компонент, не описанный в плане | `architecture.md` → дерево компонентов |
| Изменил модель данных | `data-models.md` |
| Нашёл проблему в дизайне | Заметки в `task.md` текущей задачи |
| Завершил задачу | `task.md` → `done.md` |
| Принял архитектурное решение | `architecture.md` + заметки в task |

### 3.3 Порядок чтения документации при старте сессии

```
1. rules.md          ← Ты здесь. Правила работы
2. task.md           ← Что сейчас в работе, что осталось
3. done.md           ← Что уже сделано (не повторяй)
4. plan.md           ← Общий план и стек
5. architecture.md   ← Конвенции кода
6. phase-{N}-*.md    ← Детали твоей текущей фазы
7. data-models.md    ← Модели данных (при необходимости)
```

### 3.4 Восстановление контекста после обрыва сессии

Если сессия оборвалась или агент перезапущен:

1. **Прочитай `task.md`** — найди задачи со статусом `🔨 IN PROGRESS`
2. **Прочитай `done.md`** — пойми, что уже завершено
3. **Проверь файловую систему** — какие файлы реально существуют в `src/`
4. **Сопоставь** task.md с реальным состоянием кода
5. **Обнови task.md** — если задача фактически завершена (файлы есть), перенеси в done.md
6. **Продолжи** с того места, где остановился предыдущий агент

> **ВАЖНО:** Никогда не начинай задачу заново, если предыдущий агент уже частично её выполнил. Всегда проверяй `src/` и дополняй существующий код.

## 4. Правила коммуникации между агентами

### 4.1 Конфликты

- Если два агента претендуют на одну задачу — приоритет у того, кто первый обновил task.md
- Если задача блокирована зависимостью — НЕ начинай работу, жди завершения зависимости
- Если нужно изменить код другого агента — опиши изменение в заметках task.md

### 4.2 Передача задач

При передаче задачи другому агенту:
1. Обнови `progress` в task.md — отметь, что сделано
2. Добавь в `заметки` — что осталось, какие проблемы
3. Смени `assignee` на "не назначен"
4. Смени статус на `📋 BACKLOG`

## 5. Правила проверки качества

Перед тем как пометить задачу как `✅ DONE`:

- [ ] Код соответствует конвенциям из `architecture.md`
- [ ] Компонент рендерится без ошибок
- [ ] Используются правильные цвета редкости из `rarities.js`
- [ ] Адаптивность проверена (базово — sm, md, lg)
- [ ] Нет захардкоженных строк, которые должны быть в константах
- [ ] API вызовы идут через `src/api/` модули
- [ ] Все созданные файлы записаны в done.md

## 6. Приоритеты и зависимости

```
Фаза 1 (Фундамент) ─────┐
                         ├─→ Фаза 2 (Auth) ─────┐
                         │                       ├─→ Фаза 3 (Кейсы) ───→ Фаза 4 (Инвентарь) ───→ Фаза 5 (Маркет)
                         │                       │
                         │                       └─→ Фаза 6 (Кошелёк) ─── может параллельно с 4-5
                         │
                         └─→ Фаза 7 (Полировка) ─── только после 1-6
```

**Железное правило:** Не начинай фазу N, пока фаза N-1 не завершена (исключение: фазы 4-6 могут частично перекрываться).
